# BPI-R4 Pro 8X (MT7988A) на OpenWrt: пропадающие PCIe-устройства и Wi-Fi ~20 Мбит/с через LTE — причины и решения

Плата: Banana Pi BPI-R4 Pro 8X (MT7988A), OpenWrt SNAPSHOT (r365xx), ядро 6.18.52.
Устройства на PCIe: карта Wi-Fi BE14 (MT7996, 2 линка) и два NVMe SSD. Интернет через LTE-модем Quectel RM520N-GL (USB, QMI, ModemManager).

## 1. После перезагрузки пропадают NVMe или Wi-Fi (PCIe link down)

**Симптом.** После тёплой или холодной перезагрузки случайно не поднимается часть PCIe-контроллеров:
в `dmesg` видно `11280000.pcie: PCIe link down, current LTSSM state: detect.active (0x1000001)`
(иногда `detect.quiet`). Пропадает то SSD, то Wi-Fi, иногда всё сразу. На стоке нормально загрузилось 2 раза из 6.

**Причина.** Это не драйвер и не тайминг PERST#, а тактирование.
Опорные клоки PCIe из topckgen `pextp_p0_sel … pextp_p3_sel` (26 МГц, по одному на порт) нужны
контроллерам, но в upstream DTS узлы PCIe их не заявляют. Поэтому ядро считает их «неиспользуемыми»,
и `clk_disable_unused()` (late_initcall_sync) выключает их. Проба `mtk-pcie-gen3` при этом идёт
асинхронно и с отложенным стартом (~6,5 с), а отключение клоков приходит через 50–440 мс после
начала пробы, прямо во время тренировки линка. Кто успел поднять линк, тот работает, остальные падают.
Отсюда и случайность. В SDK MediaTek эти клоки подключены к узлам PCIe и помечены критичными,
поэтому на вендорских прошивках проблемы нет.

**Решение (любое из двух):**

- Без пересборки: добавить `clk_ignore_unused` в bootargs U-Boot. Параметр хранится в окружении
  U-Boot, sysupgrade его не стирает.
  ```sh
  fw_printenv -n bootargs          # посмотреть свои текущие bootargs
  fw_setenv bootargs "<ваши текущие bootargs> clk_ignore_unused"
  ```
  Результат: 17 из 17 загрузок без сбоев на своей сборке, затем ещё 4 из 4 на официальном snapshot.
- С пересборкой: патч, который помечает `CLK_TOP_PEXTP_P0..P3_SEL` в
  `drivers/clk/mediatek/clk-mt7988-topckgen.c` флагом `CLK_IS_CRITICAL` (как в SDK MediaTek).
  Результат: 16 из 16 загрузок (1 после прошивки, 10 тёплых, 5 холодных) без `clk_ignore_unused`.

Бэкпорт upstream-фиксов тайминга PERST# (22fc8822) и `.shutdown` (7a0e17e7) на этой плате
не помогает. Проверено.

Минус своей сборки ядра: `apk add kmod-*` перестаёт работать (другой хеш ядра). Поэтому
практичнее официальный snapshot + `clk_ignore_unused`.

## 2. Wi-Fi не быстрее ~20 Мбит/с, хотя по кабелю 100+ (WAN через LTE)

**Симптом.** Интернет от LTE-модема. Клиент по кабелю получает 100–200 Мбит/с, любой клиент по Wi-Fi —
около 20. Замена карты BE14 rev 1.0 на rev 2.1 ничего не меняет.

**Что показали замеры (одно и то же время, один и тот же Mac):**

| Путь | Скорость |
|---|---|
| роутер → Wi-Fi → Mac (файл с самого роутера) | ~617 Мбит/с |
| интернет → роутер (скачивает сам роутер) | ~105 Мбит/с |
| интернет → роутер → кабель → Mac | ~85–114 Мбит/с |
| интернет → роутер → Wi-Fi → Mac | ~17 Мбит/с, в 4 потока в сумме ~22 |

То есть Wi-Fi исправен (617 Мбит/с), модем исправен (100+ по кабелю), а режется только трафик
из LTE в Wi-Fi, причём общий объём, а не отдельный поток.

**Причина.** Оператор (у меня Yota) помечает весь входящий трафик DSCP **AF11** (`tos 0x28`).
Кабелю эта метка безразлична, а mac80211 по DSCP выбирает очередь WMM:
AF11 → приоритет 802.1d 1 → **AC_BK (Background)**, самая низкоприоритетная очередь Wi-Fi.
Весь интернет-трафик клиентов Wi-Fi шёл через неё. Файл с самого роутера меток не имеет
и шёл в обычную очередь, поэтому локальный тест был быстрым.

**Как проверить у себя** (пока что-нибудь качается):
```sh
apk add tcpdump-mini
tcpdump -i wwan0 -nn -v -c 20 'tcp and src port 443' 2>/dev/null | grep -o 'tos 0x[0-9a-f]*' | sort | uniq -c
```
`tos 0x0` — меток нет. Любое другое значение (0x20, 0x28, …) — оператор помечает трафик.

**Решение.** Стирать метку на входе с модема. Файл `/etc/nftables.d/20-wwan-dscp-reset.nft`:
```
chain wwan_dscp_reset {
	type filter hook prerouting priority mangle; policy accept;
	iifname "wwan*" ip dscp set cs0 counter
	iifname "wwan*" ip6 dscp set cs0 counter
}
```
```sh
fw4 check && fw4 reload
echo /etc/nftables.d/20-wwan-dscp-reset.nft >> /etc/sysupgrade.conf
```
Если WAN у вас не `wwan0`, поправьте имя интерфейса (`ip route | grep default`).

Результат: одним потоком по Wi-Fi 17 → 86–92 Мбит/с, в 4 потока 22 → 137 Мбит/с,
то есть на уровне кабеля; дальше упирается уже в LTE.

## Попутно

- Карта BE14 и её ревизия тут ни при чём, сигнал и мощность в норме (20/20/23 дБм, HE-MCS 11 2x2).
- Если 6 ГГц не поднимается (`hostapd: Unable to setup interface`), проверьте, что у этого радио
  `band='6g'`, а не `5g`: ширина 320 МГц бывает только в 6 ГГц.
- У модема через ModemManager в `network.<iface>.device` лучше указывать путь sysfs
  (`mmcli -m any -K | grep modem.generic.device`), а не D-Bus-путь `/org/freedesktop/ModemManager1/Modem/N`:
  тот меняется, и интерфейс перестаёт подниматься после перезагрузки.
